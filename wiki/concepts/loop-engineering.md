# 루프 엔지니어링

루프 엔지니어링은 사람이 "이것도 고쳐 줘"라고 반복해서 시키는 그 일까지 AI에게 넘겨, 결과물이 기준에 닿을 때까지 스스로 돌게 만드는 기술이다. 앞선 단계의 기법들이 AI가 무엇을 보고 무엇을 지킬지를 정했다면, 여기서는 몇 번 더 돌릴지를 판단하는 몫까지 자동화한다. 사람이 중간에 끼어들지 않는 만큼 어디서 멈출지와 무엇으로 합격을 판정할지를 미리 정해 두는 일이 그만큼 중요해진다.

**루프 엔지니어링은 사람의 반복 프롬프트조차 AI에게 대체시켜, 하나의 기능을 사람 개입 없이 끝까지 완성도를 끌어올리는 기술**이다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]). 진화 서사 프롬프트 → 컨텍스트 → 하네스 → 루프에서 가장 최근에 나온 네 번째 축으로 소개된다.

## 핵심: 대립이 아니라 중첩

라프(Ralph) 루프 → [[concepts/harness-engineering|하네스 엔지니어링]] → 루프 엔지니어링은 서로 대립하는 게 아니라 중첩되는 흐름이다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).

- **라프 루프 (가장 먼저, 작년경)**: 롱러닝 에이전트 개념이 없던 시절, 에이전트를 오랫동안 반복 실행하기 위한 단순·무식한 기법. PRD나 체크포인트를 만들고 매 작업 후 휴먼 인 더 루프가 끼어들어야 했는데, 그 중간 개입을 없애려 "알아서 계속 반복해라"는 식으로 만들어졌다. 컨텍스트가 차면 성능이 떨어지는 "니들 인 헤이스택"(컨텍스트 디그라데이션) 문제 때문에, 작업을 잘게 쪼개 결과만 디스크에 저장하고 새 컨텍스트의 새 에이전트로 다음 작업을 이어가는 것이 핵심이었다. 완성도가 아니라 0→10 진행(progress)에 포커스 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).
- **하네스 엔지니어링 (그다음)**: 정해진 스코프 안에서 무엇을 하고 하면 안 되는지를 정의하는 제약 방식 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).
- **루프 엔지니어링 (가장 최근)**: 프롬프팅하는 나 자신을 줄이는 것.

## 무엇을 줄이는가: n번째 프롬프트

루프 엔지니어링의 "프롬프트하지 마라"는 첫 번째 프롬프트를 없애라는 게 아니다. 첫 프롬프트는 반드시 있어야 한다. A라는 기능을 만들었는데 결과가 만족스럽지 않아 다시 개선 프롬프트를 넣는 — 그 **두 번째·세 번째·n번째 프롬프트**를 자동화로 줄이라는 뜻이다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]). 동작 패턴은 "행동(Act) → 관찰(Observe) → 결정(Decide) → 반복(Repeat)"이며, 루프가 돌 때마다 만들고 싶은 기능의 완성도가 계속 올라간다. 즉 **무에서 유를 창조하는 게 아니라 정해진 하나의 목표의 완성도를 높여 가는 방식**이다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).

데모로 고양이 이미지를 순수 HTML 캔버스+자바스크립트로 모사하는 루프가 제시된다: 매 회차 직전 최고 결과를 비평 반영해 수정 → 헤드리스 렌더링으로 관찰 → 원본과 유사도 점수(0~100) 측정 → 비평을 JSON에 기록 → 반복. 유사도 90%를 통과 기준으로 두고 23회차까지 돌리니 입체감과 완성도가 크게 올라갔다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).

## 모두에게 맞는 건 아니다 (스코프 경고)

[[entities/boris-cherny|보리스 체르니]](보리스 체르니)가 "My job is loops"라 했다고 언급되지만 — **직함·발언 주체가 자막상 불명확함**(자막은 "Vercel CEO"·"보리스 체니" 등으로 혼동 표기, → 표준 슬러그 사전 교정 참조) — 그는 [[entities/claude-code|Claude Code]]처럼 어마어마하게 큰 프로젝트를 다룬다. 큰 프로젝트에서 새 피처가 기존 기능과 완벽히 융화되고 다른 걸 깨지 않는지 판단하는 것은 매우 중요하고 반복적이라 루프 엔지니어링이 빛난다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).

반면 사이드 프로젝트·MVP·PMF 탐색 단계의 작은 프로젝트에서는, 프론티어 모델 성능이 워낙 좋아 한 번에 `ultra code`나 max로 끝낼 수 있는 작업을 굳이 루프로 반복하면 루프 짜는 시간·도는 시간·토큰만 낭비된다. SVG처럼 한 번에 그릴 수 있는 걸 루프로 돌리는 건 말이 안 된다. **작업·프로젝트 규모와 본인 실력·이해도에 맞는 기법(right tool for the right job)을 써야 한다** (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).

## 다시 하네스로 회귀

피터 스타인버거(자막상 표기, [[entities/peter-steinberger|피터 슈타인버거]] / 오픈클로 창업자로 언급)도 결국 "루프를 디자인하는" 단계, 나아가 여러 에이전트의 함대(fleet)를 다루는 단계로 간다고 한다. 루프를 디자인하려면 무엇을 하고 하면 안 되는지의 룰을 정확히 정의해야 하는데, 그것이 곧 **다시 [[concepts/harness-engineering|하네스 엔지니어링]]으로 돌아오는 것**이다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]). 영상은 "새 개념들은 사실 앱스트랙션이 높아진 것일 뿐 완전히 새로 생긴 건 많지 않다"며, 트렌드에 휩쓸리지 말고 자기 작업 규모에 맞춰 기법을 도입하라고 조언한다 (→ [[sources/youtube-z-3BRkxQ5GM|#25 루프 엔지니어링]]).
