# 이력서에 AI 활용 경험 쓰기

이 위키의 하네스/검증/역할분리 개념을 **취업·이직 이력서 표현으로 번역**하는 응용 관점이다. 핵심 명제는 단순하다 — **"AI를 썼다"는 더 이상 변별점이 아니고, "AI가 안전하게 일할 개발 환경(=[[concepts/harness-engineering|하네스]])을 구축했다"가 변별점이 된다** (→ [[sources/youtube-wa6ZoLlnB60]]). "클로드를 활용해 개발", "코덱스로 생산성 향상" 수준은 이제(애초에) 의미가 없으며, 중요한 건 AI를 **실무적으로 어떻게** 다뤘는지다.

## 왜 "AI 썼다"로는 부족한가

이력서·포트폴리오에 AI 활용 경험을 적는 사람이 급증하면서, 단순히 "AI를 써 봤다"는 진술은 변별력을 잃었고 오히려 구체성이 없으면 역효과를 낼 수 있다 (→ [[sources/youtube-wa6ZoLlnB60]]). 회사 실무가 원하는 사람은 "AI에게 코드를 시켜본 사람"이 아니라 "AI가 안전하게 일할 환경을 구축할 수 있는 사람"이다. 이는 [[concepts/developer-role-change]]의 "선수 → 감독" 상향 이동과 정확히 같은 메시지로, 변별의 축이 **구현 능력 → 환경 설계 능력**으로 옮겨갔음을 이력서 차원에서 드러낸 것이다.

## 세 가지 축 (그대로 이력서 항목이 됨)

영상은 개인 토이 프로젝트에도 적용 가능한 세 가지를 제시한다. 각 축은 기존 위키의 하네스 개념과 1:1로 대응한다.

### ① 계획-승인 흐름 (Plan + Human Approval Gate)
"회원가입 API 만들어 줘"처럼 바로 구현시키면, AI가 의도치 않은 파일까지 바꾸거나 기존 API 응답 포맷을 바꾸거나 테스트 없이 구현할 위험이 있다. 대신 **"구현하지 말고 기존 구조를 먼저 파악한 뒤 작업 계획과 리스크만 정리해 줘. 내가 승인하기 전까지 파일을 수정하지 마"**라는 흐름을 만든다. 이는 [[concepts/verification-automation]]에서 강조하는 **구현 전 플랜 단계 검증**과 같은 원리다 (→ [[sources/youtube-wa6ZoLlnB60]]).
> 이력서 예: *"AI 코드 생성 시 작업 범위 이탈·변경 리스크 방지를 위해 플랜 우선 워크플로우와 휴먼 승인 게이트를 적용해 개발 안정성 향상"*

### ② 역할 분리 (Researcher / Planner / Reviewer)
하나의 AI에 조사·구현·리뷰·디버깅을 다 시키면 결과가 흔들린다. 회사의 기획자·개발자·리뷰어·QA가 다르듯 AI도 역할을 나눈다 — 리서처는 조사만, 플래너는 계획만, **리뷰어는 직접 수정하지 않고 문제점만 찾는다**. "리뷰어가 코드를 고치는 순간 그건 리뷰가 아니라 또 하나의 구현이 되고 **검증자가 사라진다**." 이는 [[concepts/verification-automation]]의 생성/검증 분리와 [[concepts/subagents-agent-teams]]의 역할별 에이전트 오케스트레이션을 인사이드 관점에서 강화한다 (→ [[sources/youtube-wa6ZoLlnB60]]).
> 이력서 예: *"리서처·플래너·리뷰어 역할을 분리한 AI 개발 워크플로우를 구성해 구현과 검증 과정을 독립적으로 운영"* (영상은 여기서 더 들어가면 수치까지 쓸 수 있다며 후속 영상 예고)

### ③ 프롬프트·도구 사용 로그 (추적성)
결과물이 잘 나와도 "왜 그렇게 나왔는지" 설명을 못 하면 실무적으로 운용했다고 보기 어렵다 — 문제가 생겼을 때 원인 추적이 안 되기 때문이다. 어떤 질문을 했고, AI가 어떤 파일을 읽고 어떤 명령을 실행했는지를 **로깅 [[concepts/hooks|훅]]**으로 남기면 AI 작업을 블랙박스로 두지 않고 **재연성·디버깅 가능성·운영성**을 확보한다 (→ [[sources/youtube-wa6ZoLlnB60]]).
> 이력서 예: *"프롬프트 및 로깅 훅을 구축해 AI 에이전트 작업의 재연성 및 오류 원인 추적 가능성 향상"*

> **동일 문구 재등장(강화)**: 같은 채널(생각등대)의 후속 영상 [[sources/youtube-SsHGSf_nzrI]]에서도 **글자 그대로 같은 이력서 문구**가 권장된다. 거기서는 회사가 AI 도입을 공식 지원하지 않아도 **개인 계정으로, 브랜치를 따로 파서 실험**하고 기존 코드 대비 시간 단축·품질 개선을 기록해 "실무 안에서 AI를 적용한 흔적"을 의도적으로 만들라는 실천법으로 제시된다. 경력자가 물경력을 이직 가능한 경력으로 바꾸는 맥락은 [[concepts/career-pivot-strategy]] 참조.

## 토이 프로젝트에도 적용 가능

거창한 대기업 프로젝트가 아니어도 된다. 스프링부트 프로젝트 하나에 플랜 워크플로우를 붙이고, 에이전트 역할을 나누고, 프롬프트 로그를 남기고, 위험 명령을 막는 훅을 만들면 그것은 단순 토이 프로젝트가 아니라 **"AI 시대의 개발 프로세스를 직접 설계해 본 프로젝트"**가 된다 (→ [[sources/youtube-wa6ZoLlnB60]]). 면접에서 풀어낼 수 있는 강한 경험이 핵심이며, 셋 중 하나라도 직접 해 보고 쓰는 것이 권장된다.
